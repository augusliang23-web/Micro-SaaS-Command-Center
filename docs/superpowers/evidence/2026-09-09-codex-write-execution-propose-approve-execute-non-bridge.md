Begins closing the "AI-tool interaction gap" ([[project-ai-tool-interaction-gap]]) flagged during the 2026-09-06 Drawer redesign: `CodexHandoffPanel` had real dispatch machinery behind it but only ever ran a hardcoded, read-only demo task. This required a real safety-scope conversation before any code, conducted over three rounds of `AskUserQuestion`:
1. Must see a plan/diff before real execution (not fire-and-forget).
2. Execution may edit files and run tests, but must never commit or push.
3. Start with exactly one pilot project (this repo, Micro-SaaS-Command-Center itself), everything else stays read-only; use the existing OpenAI Codex CLI integration, not a new adapter.

Went through `EnterPlanMode`/`ExitPlanMode` given the safety stakes and multi-file scope, after directly reading every file in the existing handoff pipeline (`codexHandoff.mjs`, `codexHandoffService.mjs`, `codexHandoffRoutes.mjs`, `codexAppServerClient.mjs`, `CodexHandoffPanel.tsx`, and the existing 25-test safety suite in `test/zero-copy-handoff.test.mjs`) to ground the plan in what was actually there rather than guessing.

## Key discovery that shaped the design

The existing pipeline was **deliberately** hard-locked to read-only at two independent layers — not an oversight:
1. `src/bridge/codexHandoff.mjs`'s `validateDispatch()` rejected any `task_classification` other than `READ_ONLY_REPOSITORY_INSPECTION` and any `authorized_actions` other than exactly `['repository_read']`.
2. `server/codexAppServerClient.mjs` hardcoded `sandbox: 'read-only'` in every `thread/start` call to the real Codex CLI — the CLI's own OS-level sandbox, a second, independent enforcement layer.

Opening real write execution meant deliberately relaxing both layers for one classification only, while adding equally real (not just prompt-level) enforcement of the "no commit, no push" rule.

## What shipped

- **`src/bridge/codexHandoff.mjs`** — added a second task classification, `WORKSPACE_WRITE_EXECUTION`, alongside the untouched `READ_ONLY_REPOSITORY_INSPECTION`, via a `TASK_CLASSIFICATION_RULES` table. It requires exactly `['repository_read', 'file_write', 'command_execute']` in `authorized_actions`, requires the `no-commit-no-push` constraint (instead of `read-only`), and — critically — is only accepted for a project explicitly marked `write_enabled: true` in the server-side allowlist; every other project is rejected regardless of what the client sends. Added `'git_commit'` and `'git_push'` to `CANONICAL_PROHIBITED_ACTIONS`, which every dispatch (both classifications) must already declare — real, tested enforcement, not a suggestion. `formatHandoffPrompt()` now appends an explicit "do not run git commit / git push under any circumstances" instruction for write-execution handoffs specifically.
- **`server/codexAppServerClient.mjs`** — `start()` gained a `sandbox` parameter (defaults to `'read-only'`, so every existing caller and test is unaffected), threaded into the real `thread/start` request instead of the previous hardcoded literal.
- **`server/codexHandoffService.mjs`** — threads `sandbox: 'workspace-write'` only for `WORKSPACE_WRITE_EXECUTION` handoffs. Added a real, best-effort post-completion verification step: reads the repo's HEAD SHA before dispatch and again after the turn reaches a terminal state (`git rev-parse HEAD` via `node:child_process`), and if it moved, surfaces a loud `⚠️ Verification: HEAD moved from X to Y despite the no-commit instruction` warning in the handoff's status — checking, not trusting, consistent with this app's existing fail-closed provenance philosophy.
- **`.bridge/codex-projects.local.json`** (new, gitignored, not committed) — the allowlist file `server.ts` already looked for and never found in this checkout, which is why the entire route silently returned `BLOCKED_ENVIRONMENT` before today. One entry for the real connected project (`proj-micro-saas-command-center-3808`, matching this repo's actual GitHub-connected project id — not the older `proj-command-center` fixture entry, which has a fake `github.com/my-org/...` repository and was never a candidate), `write_enabled: true`, `cwd` pointing at this checkout.
- **`src/components/CodexHandoffPanel.tsx`** — rewritten around two explicit phases. "請 AI 先規劃怎麼做" dispatches a `READ_ONLY_REPOSITORY_INSPECTION` handoff built from the project's real `currentTask`/`blocker`/`nextAction` (replacing the old hardcoded "read-only-smoke" demo objective) asking Codex to propose, not execute. Once that completes, the returned plan renders and a second, visually distinct "核准並執行" button appears — only then — which dispatches a `WORKSPACE_WRITE_EXECUTION` handoff embedding the approved plan text as its objective/context. A persistent line ("AI 會先規劃、你確認過才會真的執行；只能改檔案跟跑測試，不會自動 commit 或 push") states the boundary in the UI itself, not just the backend.

## Known gaps / deliberately out of scope (unchanged from the approved plan)

- `ChatGPTBridgeModal`'s "apply decision" flow is not wired into this pipeline — connecting a human product decision into a real dispatch is a separate design question (how does a *decision* become an *objective*?), flagged for a future round.
- Codex's own native mid-turn approval requests (`approvalPolicy: 'on-request'`, the `AWAITING_INPUT` state) are not respondable — if Codex asks for a native approval mid-turn, the turn stalls exactly as before (an honest "stuck, needs a human" state), not silently proceeds. The existing test asserting approvals are never auto-approved (`test/zero-copy-handoff.test.mjs`) is unchanged and still passes.
- Every project except the one pilot remains exactly as read-only-only as before — no behavior change for them.
- The "no commit/push" rule is enforced at three independent layers (server-side `CANONICAL_PROHIBITED_ACTIONS` validation, an explicit prompt instruction, and post-hoc real git verification) but not at the OS/sandbox level itself — Codex CLI's `workspace-write` sandbox permits local git operations; only network access is independently restricted by the CLI's own sandbox (which is what would actually block a real `git push`, not this app's own enforcement). This is a real, understood limitation, not an oversight — recorded here so it isn't mistaken for airtight OS-level prevention.
